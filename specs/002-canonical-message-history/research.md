# Phase 0: Research & Root-Cause Analysis

## Bug 1: Date grouping relies on `created_at`

**Issue**: In `App.jsx`, `ChatArea.jsx`, and `MessageList.jsx`, the UI uses `formatDate(msg.created_at || msg.time)` to generate date dividers and group messages. But `created_at` in the backend is `new Date().toISOString()` representing the exact moment the message was inserted into SQLite, not the message's historical time. Thus, all synced historical messages fall under "Hôm nay".

**Decision**: 
The backend and frontend must standardize on `timestamp_ms` as the sole source of chronological truth.
- Backend: On insert, `created_at` will be explicitly derived from `timestamp_ms` if it exists.
- Frontend: `MessageList.jsx` and `App.jsx` will be updated to use `timestamp_ms` for both sorting and date grouping.

## Bug 2: Accessibility labels in content

**Issue**: Facebook accessibility labels like "Tin nhắn do Bạn gửi lúc Thứ Sáu 10:09 sáng: Chào em" are parsed directly as bubble content in `content.js` and `background.js` because the inner `span` lacks a clear divider.

**Decision**:
Update `textFilter.js:cleanMessageText()` to use a stricter regex that targets the exact patterns generated by Facebook DOM.
Regex to add/enhance: `/^Tin nhắn do .+? gửi lúc [^:]+:\s*/i` and `/^Message sent by .+? at [^:]+:\s*/i`.
If a message after filtering is empty, it must be completely discarded by the parsers before being sent to the backend.

## Bug 3: Non-deterministic IDs cause duplicates

**Issue**: In `background.js` history sync, the fallback `deterministicId` includes `bubble_idx` and `dom_order` which may shift between syncs if intermediate messages were loaded or deleted. Also, real-time fallback IDs in `server.js` (for XHR/Mercury) use `Date.now()` which creates a new ID on every reload.

**Decision**: 
For history sync, `deterministicId` should be derived strictly from a content hash + sender + `timestamp_ms` bucket (nearest minute) rather than DOM order index, unless a native `data-id` exists. `ConversationRepository.fingerprint()` already does this and should be leveraged as the final fallback on the server.

## Bug 4: Server startup and test suite failures (P0)

**Issue**: 
1. Syntax error due to `const targetAccountId` duplicate declaration.
2. Unsafe migration backup for `version === 0` in `db.js`.
3. SQLite `integrity_check` returns `"ok"` string, not an array.

**Decision**:
Before executing the canonical message history feature, these P0 bugs will be fixed in `server.js` and `db.js`, and the integration tests will be wired to `testDatabase.js` to ensure the regression suite actually runs SQLite operations.
