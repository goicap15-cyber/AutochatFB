## Phase 5 — User Story 3: Confirm delivery and recover safely (P1)

- [X] T018 `OutboundConfirmationService`/`OutboundDomCorrelationService` manifest correlation — **found and fixed a real, would-have-shipped bug**: `matchPendingImageOutbound`'s query only ever checked `attachment_id IS NOT NULL`, so a manifest dispatch (`attachment_id` NULL, only `manifest_id` set) was **completely invisible to Facebook-confirmation matching** — a real, successful multi-file/folder send would have stuck at "pending" forever, exactly the class of bug fixed earlier this session for plain text. Fixed by also matching `manifest_id IS NOT NULL`. Caught by `campaignFileTransport.test.js`'s confirmation test before ever reaching a real send; pinned separately at the unit level in `outboundDomCorrelation.test.js`. Deliberately did **not** build per-file correlation (matching a specific member within a manifest) — a DOM image/file observation carries no recoverable checksum/id to match against, so correlation is (and was already, for single attachments) "thread has a pending attachment, confirm the one active attempt" - sufficient because there is only ever one active attempt per recipient at a time (FR-011's guarantee), not because every file is individually confirmed.
  - **Second, more serious false-positive bug found during the live send itself (2026-08-17)**: sent a real 2-file manifest ("note1.txt", "note2.txt") + caption to Mang Bảo Khánh (Page). The DB ended up fully "sent"/"confirmed" with a real `fb_message_id`, but the Business Suite screenshot the user confirmed with only shows the caption bubble — no visible file attachment element at all, unlike this same thread's earlier rich-image tests which do render as a distinct bubble. Root cause: `matchPendingOutboundByRawContent` (the early junk-collapse-rescue match) and the legacy content-match query in `server.js`'s `NEW_MESSAGE_RECEIVED` handler both matched **purely on caption text**, with no check on whether the dispatch they were about to confirm had an `attachment_id`/`manifest_id` at all. A caption rendering on Facebook only proves the text sent - it is not evidence the file(s) riding with it actually attached. **Fixed**: both queries now `LEFT JOIN message_queue` and refuse to match any pending row whose queue entry has `attachment_id` or `manifest_id` set - such dispatches can now only be confirmed through the explicit media path (`matchPendingImageOutbound`), and fail safe to `'unknown'` on timeout instead of falsely reporting `'sent'`. Regression test: `campaignFileTransport.test.js` "a caption-only DOM text match never confirms a pending manifest dispatch...". Full suite re-verified green (311/311, 3 consecutive runs) after the fix.
  - **Follow-on gap, found once the actual send mechanism was fixed (see T020)**: after T020's fixes made a real 2-image manifest send succeed end-to-end on Facebook, the DB still showed only a plain text confirmation event (`media_type: 'text'`) for it, not a media one. Root-caused (2026-08-18) to `page_content.js`'s `resolveMessageContent` (the Business Suite/Page DOM observer - `content.js` is the separate personal-Messenger observer, not this path): it returned on the wrapper's `fullText` alone and never even checked for an `<img>` when both were present in the same `[data-message-id]` node - a shape that only arises for a caption sent alongside a file-transport image (the dedicated rich-image path apparently renders caption+photo as two separate wrapper nodes, per `content.js`'s own comment about personal Messenger doing the same, so this combined-node shape hadn't been hit before). **Fixed**: `resolveMessageContent` now checks for a real (empty-alt) `<img>` before the `fullText` early-return, returning `kind: 'media'` with the caption text passed through as `caption` - `forwardResolvedMessage` already supported this shape (`text = isMedia ? resolvedContent.caption : resolvedContent.text`), so no downstream changes were needed. Also required loosening `server.js`'s `isMediaConfirmation` check (extracted to a new testable `OutboundDomCorrelationService.isMediaConfirmationEvent(m)`, pinned in `outboundDomCorrelation.test.js`), which previously required an *empty* caption to treat an event as media - now any real media evidence (`media_url` or a non-`'text'` `media_type`) counts regardless of caption. Net effect before this fix: a genuinely successful file-transport image send couldn't be recognized as sent - it timed out to `'unknown'` (safe, no lie) but **`QUEUE_CONFIRMATION_TIMEOUT` is in `CampaignRunner.RETRYABLE_ERRORS`, so the campaign would automatically retry and send the same file(s) again for real**. This was the last blocking issue for going live; see T020 for the full fix and the pending final live re-verification.
- [X] T019 `server.js` confirmation handling — no manifest-specific change needed; `OutboundDomCorrelationService.confirmPendingOutbound` (already atomic: message + queue status in one call) works unchanged for a manifest dispatch once T018's matching fix landed. Verified end-to-end in `campaignFileTransport.test.js`'s confirmation test, including replay-safety (a second confirmation for the same `fb_message_id` is a no-op).
